## Goal

Define every Phase 1 output format and the code interfaces, so P1-03..P1-07 can run in parallel on disjoint files.

Read KICKOFF.md "Phase 1" for the required outputs:

- `ui-spec/visio-2016.yaml`, `ui-spec/visio-365.yaml`: tabs → groups → controls, plus backstage and context menus. Per control: `id`, `type`, `label`, `parent`, `order`, and reserved empty optional fields `bounds`, `icon_ref`, `keytip`, `size_variant`, `visual_notes` for the later screenshot pass. The format must let that pass enrich data **without schema changes**.
- `ui-spec/schema.json`: JSON Schema validating both layout files.
- `ui-spec/commands.yaml`: our command ids → VisUICmds names and control ids, each with `mapping_confidence: exact | inferred | unknown`.
- `ui-spec/shortcuts.yaml`.
- `ui-spec/diff-2016-vs-365.md`: generated structural diff.
- ShapeSheet table (sections, rows, cells, types, default units) as codegen input for `crates/model`. Choose its path and format.
- `docs/vsdx-inventory.md`: every MS-VSDX part, element and attribute with MVP status supported / preserved-only / later.
- `docs/parity/controls.md`: generated matrix of every control id in both layouts with status implemented / stub / out-of-scope.
- One command, `cargo xtask extract`, regenerates all of it from `reference/`.

## Decisions to make (one ADR each where significant)

1. **Command id scheme** (e.g. `home.align.left`, `shape.rectangle`, `file.save`) and how ids relate to Fluent control ids and VisUICmds names. Every user action is a command in one registry (AGENTS.md section 6).
2. **ui-spec YAML format and JSON Schema**, including how 2016 and 365 layouts share or differ in control ids, and how backstage/context menus are represented. Note which YAML crate the loader uses (licence must pass `deny.toml`) and how the schema is validated in tests (e.g. `jsonschema` crate).
3. **ShapeSheet table format and location**, and how `crates/model` will consume it in Phase 2 (build.rs codegen vs checked-in generated Rust).
4. **Extraction architecture**: module per source under `xtask/src/extract/`, input paths under `reference/`, deterministic output (sorted, stable), how labels are kept short (labels only, never descriptions — clean-room rule 4), what happens when `reference/` is missing (clear error, not panic).
5. **libvisio oracle harness**: build approach (CMake/autotools prerequisites, where the build lives on /Volumes/Dara), how tests invoke it, and that it is optional for the gate (skipped when not built).
