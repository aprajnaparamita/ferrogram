## Goal

Produce three Phase 1 outputs from their respective reference
sources:

1. `ui-spec/commands.yaml` — the Ferrogram command registry's
   mapping table. Each entry maps a Ferrogram command id to its
   VisUICmds constant and to its Fluent control names. See
   ADR 0006 and ADR 0007.
2. `ui-spec/shapesheet.toml` — the canonical catalogue of every
   ShapeSheet section, row, and cell that Ferrogram knows about.
   See ADR 0008.
3. `ui-spec/shortcuts.yaml` — the keyboard shortcut table. See
   ADR 0007.

The merge file `xtask/src/extract/commands.rs` is new (it doesn't
have a P1-02 stub because the merge is only useful once P1-03 has
written the layouts). It calls `visuicmds::run` and reads the
P1-03 layouts from `ui-spec/`, joins them on `fluent_ids`, and
writes the final `commands.yaml`. The dispatcher in
`xtask/src/extract/mod.rs` is updated to call `commands::run` after
`visuicmds` and to drop the `visuicmds` row from the per-extractor
output list (the dispatcher logs `commands` instead). Wire
`Schema::validate_file` for `commands.yaml` and `shortcuts.yaml`.

`crates/model/src/shapesheet_table.rs` is **not** in P1-04
ownership. ADR 0008 (M1) removed the `build.rs` and the generated
file from Phase 1; Phase 2 will introduce `cargo xtask codegen`
that turns the TOML into a committed
`crates/model/src/generated/shapesheet.rs`, with `--check` mode
that the gate runs to catch drift. The TOML is the only Phase 1
artefact; the codegen step is a Phase 2 task (the master agent
will name its id at Phase 2 planning).

## Outputs

### `ui-spec/commands.yaml`

A YAML list of command mappings, in the order:

1. VisUICmds that have a Fluent control mapping
   (`mapping_confidence: exact`).
2. VisUICmds that have only an inferred Fluent mapping
   (`mapping_confidence: inferred`).
3. VisUICmds with no Fluent mapping yet
   (`mapping_confidence: unknown`).

Inside each group, sorted by command id. The merge algorithm:

- For every VisUICmds constant `visCmd*`, derive a Ferrogram
  command id by stripping `visCmd` and lowercasing the first
  letter: `visCmdFileSave` → `file.save`. Multi-word constants are
  split on CamelCase boundaries: `visCmdAlignObjectLeft` →
  `arrange.align.object.left` (using the functional scope
  `arrange`, not the earlier-draft `align.object.left`). Override
  these splits with a small hand-written table in
  `xtask/src/extract/commands.rs::OVERRIDES` for cases where the
  CamelCase split gives the wrong scope (e.g.
  `visCmdABarAutoHeight` → `app.bar.auto_height` rather than
  `a.bar.auto.height`).
- The functional scope list is in ADR 0006: `app`, `file`, `edit`,
  `view`, `insert`, `format`, `text`, `arrange`, `shape`,
  `connector`, `page`, `layer`, `tools`, `data`, `review`,
  `developer`, `help`. The scope is the first id segment; the
  `OVERRIDES` table is the only way to land in a different scope
  than the CamelCase split would otherwise give.
- Cross-check every Fluent control name in `commands.yaml`
  against `ui-spec/panel-2016.yaml` and `ui-spec/panel-365.yaml`
  (B1: `fluent_ids` are Fluent control names, not command ids). A
  Fluent name that appears in neither is a hard error (the
  cross-check is part of `commands::run`).
- A `label` is taken from the Fluent `Control Name` if available,
  otherwise from a hand-written table in
  `xtask/src/extract/commands.rs::LABELS` for the top 100
  VisUICmds. Anything without a label uses the command id's last
  segment capitalised (e.g. `file.save` → `Save`). All labels are
  short; clean-room rule 4 still holds.
- `visuicmd` is `null` when no VisUICmds constant is known, or the
  `visCmd*` string otherwise. The schema (m1) requires
  `type: ["string", "null"]` with pattern
  `^visCmd[A-Za-z0-9]+$`; the string `"null"` and `""` are no
  longer accepted.

### `ui-spec/shapesheet.toml`

The shape is in ADR 0008. The extractor walks
`reference/ms-vsdx/office-developer-client-docs/docs/visio/`:

- Files matching `<name>-section.md` (no `cell-` substring) are
  sections. The section name is the title text before
  `(ShapeSheet)` or `(Visio)`. The `section_index` is looked up
  from `visio.vissectionindices.md`.
- Files matching `<cell>-cell-<section>.md` are cells. The cell
  name is the file's first word. The `cell_index` is looked up
  from `visio.viscellindices.md`. The `type` and `default_unit`
  are inferred from the cell's remark text using a small
  pattern-matching table in `xtask/src/extract/shapesheet.rs`.
- The four enumeration files are loaded for the integer lookups.
- The file is sorted by section name, then by cell name, then by
  row name. Output is deterministic (see the unit test).

### `ui-spec/shortcuts.yaml`

A YAML list of shortcuts. The extractor parses the HTML, finds
each `<table>`, walks the rows, and produces a `Shortcut` for
each. The mapping from a Microsoft action description ("Save",
"Undo") to a Ferrogram command id is a hand-written table in
`xtask/src/extract/shortcuts.rs::ACTION_TO_COMMAND`. Anything not
in the table is dropped with a warning to `stderr` and recorded
in the Result section. The 365 layout's command ids are preferred;
the 2016 layout's ids are used as a fallback when a 365 id does
not exist.

A header comment in the file records the Wayback snapshot URL and
the source commit.

Each shortcut has a `sequence: [[key, ...]]` field (m2): an
ordered list of chords, each chord is a non-empty list of key
tokens. A single-chord shortcut (e.g. `Ctrl+Z`) has a one-element
sequence `[["Ctrl", "Z"]]`; a multi-step ribbon keytip
(`Alt, H, F, O`) is `[["Alt", "H"], ["F"], ["O"]]`.

## Implementation notes

- **Markdown table parsing.** The VisUICmds and enumeration files
  use a stable `| Constant | Value |` table format. A small
  hand-written parser in `xtask/src/extract/markdown.rs` is enough
  — `pulldown-cmark` is overkill.
- **YAML writing.** Use **`serde-saphyr`** (MIT, pure Rust) — not
  `serde_yaml` or `serde_yml`. See ADR 0007 M5. P1-04 adds it to
  `xtask/Cargo.toml`.
- **YAML 1.1 booleans.** serde-saphyr reads plain `Y`, `N`, `on`,
  `off` (and similar) as booleans, and the schema then rejects the
  chord. Every key token in `shortcuts.yaml` must be emitted as a
  quoted string (`[Ctrl, "Y"]`). Add a round-trip test that writes
  and re-reads a shortcut with `Y`, `N`, `On` and `Off` keys. Found
  in P1-06 (open issue 3).
- **Loader check.** After writing the files, load them with
  `ferrogram_ui_spec::Loader` in a test (or run the `ui-spec` tests)
  to confirm the loader accepts them.
- **State of `main` (master note, after P1-03 and P1-05 merged).**
  `xtask` already depends on `serde-saphyr` 1.3 and `jsonschema` 0.58
  (`default-features = false`); do not add other versions. The YAML
  emitter options P1-03 uses in `xtask/src/extract/fluent.rs` keep
  the committed style; use the same options. `xtask` has a
  dev-dependency on `ferrogram-ui-spec`, so the loader check below
  can call `Loader` directly (see the P1-03 test
  `committed_layouts_load_with_the_runtime_loader`).
- **Filling control commands.** P1-03 writes every control with
  `command: null`. After `commands.yaml` is built, the commands
  extractor sets `command` on each layout control whose Fluent id
  (or alias) appears in some entry's `fluent_ids`, and rewrites both
  layout files. Run order: fluent, then commands. Re-running
  `cargo xtask extract` must stay byte-identical. A Fluent id mapped
  by two different commands is an error.
- **TOML writing.** Use the `toml` crate (already in xtask).
  Build `toml::Value::Table` and `toml::to_string_pretty`.
- **No `build.rs` in `crates/model`.** ADR 0008 (M1) explicitly
  forbids a build script that writes into `src/`. P1-04 ends at
  the committed `ui-spec/shapesheet.toml`; the codegen step is
  Phase 2.
- **Cross-check.** `commands::run` loads
  `ui-spec/panel-2016.yaml` and `ui-spec/panel-365.yaml` (which
  P1-03 already produced) and reads their Fluent control names.
  Any `commands.yaml` entry whose `fluent_ids` includes a name
  absent from both layouts is an `Err(ExtractError::Schema { .. })`.
- **License.** `serde-saphyr` is MIT, `toml` is MIT/Apache-2.0
  (already in xtask). `cargo deny check` must remain green,
  including the advisories step (the P1-02 review rejected
  `serde_yml` because of RUSTSEC-2025-0068 / RUSTSEC-2026-0333).

### Interpretations (where the task text was ambiguous)

1. **Dispatcher wiring.** The dispatcher's module list has `commands`
   in the old `visuicmds` slot (right after `fluent`); `commands::run`
   calls `visuicmds::run` for the enumeration half and no `visuicmds`
   row is logged ("drop the `visuicmds` row ... the dispatcher logs
   `commands` instead").
2. **Exact vs inferred.** `exact` = the Fluent control name equals the
   constant minus `visCmd`, **or** both sides derive the same command
   id (`Paste` / `visCmdUFEditPaste` -> `edit.paste`). `inferred` =
   word-subset match after stripping control-type words
   (`AlignLeftButton` / `visCmdAlignObjectLeft`). Fluent-only entries
   use `unknown` (ADR 0006's `insert.shape` example). Each Fluent name
   joins at most one command (multi-mapping is a hard error).
3. **Labels.** Resolved as `LABELS` (hand-written, 79 entries, the
   "top 100 VisUICmds" bound asserted by a test) first, then the
   humanised Fluent `Control Name` (CamelCase words minus a trailing
   control-type word and a leading scope word: `FileSave` -> `Save`),
   then the id's last segment capitalised (`file.save` -> `Save`). The
   task sentence puts the Fluent name first; the order is swapped so
   the ADR 0006 example labels (`Save`, `Align Left`, `Connector`,
   `Insert Shape`) come out exactly.
4. **Command-id derivation.** `visCmdAlignObjectLeft` ->
   `arrange.align.object.left` (task body). Note that ADR 0006's
   example list and the acceptance criteria say `arrange.align.left`
   for the same constant — the task body's explicit arrow was followed
   (see open issue 2). `OVERRIDES` (75 entries) fixes scope/shape
   cases, including the task's own `visCmdABarAutoHeight` ->
   `app.bar.auto_height` example and the ADR's `format.text.bold`,
   `tools.pointer`, `shape.rectangle`, `view.toggle_grid` examples.
5. **ShapeSheet naming.** Cell names come from the page title before
   `" Cell ("` (multi-word names joined: `Y Justify` -> `YJustify`),
   which matches the task's "the file's first word" for the single-word
   majority (`pinx-cell-...` -> `PinX`) and is well-defined for the
   multi-word minority. Sections are keyed typography-insensitively
   (`Action Tag` = `Action Tags`, `PrintProperties` = `Print
   Properties`, `User-Defined Cells` = `User-defined Cells`); the
   canonical name is the section page's title. How-to pages ("Add,
   Show, Hide, or Delete a Section") and the MS-VSDX `*-element*`
   schema pages are excluded by name shape and file name.
6. **`kind`.** `collection` when any cell's `Row index` metadata
   repeats (`visRowSmartTag + i`), else `object`; sections with no
   cell pages default to `collection`. `section_index` comes from the
   cells' `Section index` constants, with a name-prefix fallback for
   the cell-less sections (`Scratch`, `Fill Gradient`, `Line
   Gradient`). `Layer Membership` is kept as a section without a
   `section_index` (it is `visSectionObject`/`visRowLayerMem`, which
   name matching cannot see).
7. **`type`/`default_unit`.** Pattern table over the cell's remark
   text (first paragraph), documented in `infer_type_unit`: Bool
   ("whether"), Color ("RGB"/"color"), Degrees, Points, Percent,
   Inches ("coordinate"/"width"/...), String ("formula"/"name"/...),
   List (a `|Value|Description|` table), Number fallback. Section
   `default_unit` is the majority of its cells. The ADR's optional
   `default_value` is **not** extracted (it would mean copying prose
   fragments).
8. **Rows.** `[[rows]]` is the global `VisRowIndices` table (all 51
   constants, sorted); `section` is the first (alphabetical) logical
   section whose cells reference the row, omitted when none. A
   section's `rows` lists the `visRow*` constants its cells reference.
   The row-*type* pages (e.g. `lineto-row-geometry-section.md`) are
   recognised but not captured (they are row types, not row indices —
   see open issue 6).
9. **Shortcuts.** One `Shortcut` per table row; alternatives ("Ctrl+G
   or Ctrl+Shift+G") record the first alternative. The sequence is the
   m2 chord list (`Ctrl+Z` -> `[["Ctrl", "Z"]]`; `Alt, H, F, O` ->
   `[["Alt", "H"], ["F"], ["O"]]`; a lone modifier chord merges with
   the next step). Key tokens are canonicalised against a whitelist
   (`Ctrl`, `Shift`, `Alt`, `F1`, `Left Arrow`, `=`, ...); prose cells
   are rejected and the row dropped. `scope` comes from the section
   heading (`SECTION_SCOPES`, fallback `global`); `section` keeps the
   short heading. Every key token is emitted as a quoted string where
   YAML 1.1 would read it as a boolean (serde-saphyr quotes `Y`, `N`,
   `On`, `Off` automatically — proven by the required round-trip
   test).

### Deviations

- `xtask/src/extract/fluent.rs`: the P1-03 test
  `committed_layouts_load_with_the_runtime_loader` wrote empty
  `commands.yaml`/`shortcuts.yaml`; with filled `command` fields the

  copies the committed files when present (test-only change; the P1-03

- `visuicmds::run` signature changed (parser, see above).
- The 15 table rows whose constants carry escaped underscores
  (`visCmdSetDynConnLineJumpStyle\_2pt`, values 1708-1717) are
  **skipped**: the schema's `visuicmd` pattern is
  `^visCmd[A-Za-z0-9]+$` and cannot hold them (open issue 1).
- `ui-spec/shapesheet.toml` table order is `[enumerations]`,
  `[[rows]]`, `[[sections]]` — the `toml` serializer emits tables in
  alphabetical key order, so `rows` precedes `sections` (the ADR
  sketch shows the opposite order; the shape is unchanged).
- `commands.yaml`/`shortcuts.yaml` carry a short generated-file header
  comment (the task mandates one for `shortcuts.yaml`; the same
  treatment for `commands.yaml` keeps the "do not edit by hand" rule
  visible).

### Open issues

1. **`visuicmd` pattern vs 15 constants.** The VisUICmds table has 679
   rows; 15 of them (`visCmdSetPageLineJumpCode\_None` family and
   `visCmdSetDynConnLineJumpStyle\_2pt` family) name constants with
   underscores, which the `commands.yaml` schema pattern
   `^visCmd[A-Za-z0-9]+$` rejects. They are skipped, so
   `commands.yaml` covers the 664 constants the task/P1-01 counted.
   If those 15 commands matter later, the schema pattern (owned by
   P1-06) needs `^visCmd[A-Za-z0-9_]+$`.
2. **`arrange.align.object.left` vs `arrange.align.left`.** The task
   body derives `arrange.align.object.left` for `visCmdAlignObjectLeft`
   (followed); ADR 0006's example list and the acceptance-criteria
   parenthetical show `arrange.align.left`. Whichever is canonical, a
   one-line `OVERRIDES` entry reconciles them.
3. `docs/sources.md` (source 2) says "664 `visUICmdXxx` constants"; the
   source table has 679 rows (see issue 1). The number in the docs
   should state which count it means (master-owned file).
4. The `ACTION_TO_COMMAND` table maps ~61 of the page's action
   descriptions; the other 151 are dropped by design (navigation and
   typing rows have no Ferrogram command yet). Filling more is a
   one-line-per-action change once Phase 4 registers the commands.
5. Two "Align text" sections on the source page use different chords
   for the same command (desktop `Ctrl+Shift+C` vs web `Ctrl+Shift+S`
   for centre); both rows are kept with their own `section`.
6. Row-type pages (MoveTo Row, LineTo Row, ...) are parsed but not
   represented in `shapesheet.toml`; a future schema revision could
   add `[[row_types]]` for the Geometry-style row families.
7. `keyChord` tokens like `Arrow Keys` describe a repeated key; the
   schema accepts them (minLength 1) but a future `kind` field could
   distinguish chords from holds.

### Unmapped action descriptions (151, dropped)

The list was removed at merge (master): it quoted the support page's
action text verbatim, which AGENTS.md section 4 keeps out of the
repository. `cargo xtask extract` prints every dropped row as
`shortcuts: dropped (unmapped action): ...` on each run.
