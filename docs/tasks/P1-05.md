## Goal

Walk the MS-VSDX schema and write a `docs/vsdx-inventory.md` that lists
every OPC part, every XML element, and every attribute, with an MVP
status of `supported`, `preserved-only`, or `later`.

The output is the planning document for Phase 2 (`.vsdx` read/write)
and Phase 3 (rendering). The MVP is the Phase 2 scope: parse, preserve
unknown parts, and round-trip. "Preserved-only" means we keep the XML
verbatim without modelling it. "Later" means we know about it but
Phase 2 ignores it.

## Inputs

- `reference/ms-vsdx/office-developer-client-docs/docs/visio/schema-mapvisio-xml.md`
  — embeds the Visio 2013 XSD in a fenced code block. The XSD text
  carries a Microsoft copyright notice in `<xsd:annotation>`; **do
  not commit the XSD text**. We extract element names, type names,
  attribute names, and the parent-child tree.
- `reference/ms-vsdx/office-developer-client-docs/docs/visio/*.md` —
  the 1082 reference pages. The relevant subsets:
  - `<type>_type-complextypevisio-xml.md` (~350 files): one
    complex type per page. The first paragraph after the title
    lists the element's name, type, and a one-line description
    (short, safe to use as a label).
  - `<section>-section.md` and `<cellname>-cell-<section>-section.md`
    files: ShapeSheet metadata; P1-04 reads these, P1-05 only uses
    them to confirm the round-trip surface (no extraction here).
- `reference/ms-vsdx/[MS-VSDX].pdf` — the canonical spec text. The
  extractor does **not** parse the PDF; the markdown is the source of
  truth. The PDF is the citation for `source_revision` in the
  inventory header.

## Outputs

### `docs/vsdx-inventory.md`

A single markdown file with these sections:

1. **Header.** Source URL, XSD commit, extraction timestamp.
2. **OPC parts.** A table of every OPC part path (e.g.
   `/visio/document.xml`, `/visio/pages/_rels/pages1.xml.rels`),
   with the part's content type and a short label. One row per
   part. Status is one of:
   - `supported`: Phase 2 will read and write this part.
   - `preserved-only`: Phase 2 keeps the part byte-for-byte; it is
     never parsed.
   - `later`: not in the MVP.
3. **Complex types.** A table of every `*_type-complextypevisio-xml.md`
   page: type name, parent type, child element count, status. Same
   three statuses.
4. **Elements.** A table of every element name in the XSD, with
   `parent type`, `type ref`, `cardinality`, and status. Status is
   `supported` for elements Phase 2 will read; `preserved-only` for
   elements we keep verbatim on round-trip; `later` for everything
   else.
5. **Attributes.** A table of every attribute name in the XSD, with
   `parent element`, `type`, and status.
6. **Counts.** A summary table: total parts, supported parts;
   total types, supported types; total elements, supported elements;
   total attributes, supported attributes.

The tables are sorted (parts by path, types by name, elements by
`(parent type, element name)`, attributes by `(parent element,
attribute name)`). Output is deterministic.

### Status assignment

The default for a new element is `preserved-only` (we keep the XML,
we don't model it). The P1-05 author promotes an element to
`supported` only when the Phase 2 reader is in scope. The list of
in-scope elements is in the Phase 2 task file; for P1-05, use the
following conservative rule:

- A `<Pages>`, `<Page>`, `<Shape>`, `<Cell>`, `<Section>`, `<Row>`,
  `<Connect>`, `<Masters>`, `<Master>`, or document-properties
  element is `supported`.
- Every other element is `preserved-only` in P1-05; the master agent
  may promote specific elements to `supported` in a follow-up
  before Phase 2 starts.
- Any element under a "Theme", "Comments", "Validation", "DataRecordset",
  or "User" part is `later`.

A unit test asserts the default-status logic and the promotions above.

## Implementation notes

- **XSD parsing.** The XSD is a single fenced code block inside
  `schema-mapvisio-xml.md`. Extract the block, then parse it with the
  `roxmltree` crate (MIT) — it is a fast, pure-Rust, read-only XML
  parser. We only need `<xsd:element>`, `<xsd:attribute>`,
  `<xsd:complexType>`, `<xsd:extension>`, and `<xsd:restriction>`.
- **Markdown table parsing.** The 350 complex-type pages share one
  shape: a title, a metadata block, and a small table with `Element`,
  `Type`, and `Description` columns. A hand-written parser in
  `xtask/src/extract/markdown.rs` is enough.
- **OPC part discovery.** The XSD references part paths in the
  `app.xml` and `document.xml` schemas. Hard-code the canonical part
  list (it is a closed set per [MS-VSDX]) in
  `xtask/src/extract/vsdx_schema.rs::PARTS`. The list is:
  - `/[Content_Types].xml` (always `preserved-only`).
  - `/_rels/.rels` (always `preserved-only`).
  - `/visio/document.xml` (`supported`).
  - `/visio/_rels/document.xml.rels` (`preserved-only`).
  - `/visio/pages/pages.xml` (`supported`).
  - `/visio/pages/page1.xml` ... `pageN.xml` (`supported`).
  - `/visio/pages/_rels/pages.xml.rels` (`preserved-only`).
  - `/visio/masters/masters.xml` (`supported`).
  - `/visio/masters/master{1..N}.xml` (`supported`).
  - `/visio/windows.xml` (`preserved-only`).
  - `/visio/validation.xml`, `/visio/validation_issues.xml` (`later`).
  - `/docProps/app.xml`, `/docProps/core.xml`, `/docProps/custom.xml`
    (`preserved-only`).
  - `/visio/theme1.xml` ... `themeN.xml` (`preserved-only`; Phase 3
    parses them).
  - `/customXml/*` (`preserved-only`).
  - Any other part: `preserved-only`.
- **Clean-room.** Never embed the XSD text. The inventory records
  element names, type names, and parent-child relationships; that is
  structural data, not Microsoft's prose. The `<xsd:annotation>`
  copyright notice in the source XSD is **not** written anywhere.
  Add an extractor test that reads a fixture, runs the extractor,
  and asserts the output contains no `<xsd:` strings and no `©`
  or `Copyright` substrings.
- **Determinism.** Re-running the extractor on the same input must
  produce byte-equal output. Use `BTreeMap` everywhere and a
  dedicated test.

### Status rules as implemented (documented in the inventory header)

- Elements: `preserved-only` by default; `supported` for
  `Pages`/`Page`/`Shape`/`Cell`/`Section`/`Row`/`Connect`/`Masters`/
  `Master` and the `DocumentProperties` subtree; `later` for the
  deferred groups, which **overrides** the `supported` list inside the
  groups (e.g. `(User_Type, Row)` is `later`).
- Deferred groups mapped onto this XSD: the `Comments` subtree
  (comments part), the `Validation` root subtree (validation part),
  the `DataRecordSets` root subtree (recordsets part), the `User`
  ShapeSheet section (reached via the `<Section N="User">`
  alternative), and the theme cell types (which contain no element
  declarations — the theme group is a no-op in the elements table).
  Shared base types (`Cell_Type`, `Rel_Type`, `RefBy_Type`) do **not**
  leak into the groups: `later` is computed by reachability, so e.g.
  `(Cell_Type, RefBy)` stays `preserved-only` while
  `(UserRow_Type, Cell)` is `later`.
- Types: `supported` when a `supported` element carries the type
  (directly or via an extension base); `later` for deferred group
  entry points (`User_Type`, `Theme_Type`, `ThemeModern_Type`) or when
  every usage is `later`; `preserved-only` otherwise (including
  alternative-only cell types like `PinX_Type`).
- Attributes: the status of their declaring type; `Parent element`
  lists the elements carrying the attribute (directly or via an
  extension base).

### Deviations from the task sketch (deliberate, please review)

1. **Complex types table is XSD-driven, not page-driven.** One row per
   `<xsd:complexType>` in the embedded XSD (620 rows) with an extra
   `Doc page` column, instead of one row per `*_type-complextypevisio-xml.md`
   page. Reason: that glob matches 275 files, of which only 152 are
   complex-type pages; 123 are element-occurrence pages that Microsoft
   named with the `_type-complextypevisio-xml.md` suffix (e.g.
   `attachedtoolbars-element-documentsettings_type-...`). Every one of
   the 275 pages is still accounted for: it maps into a `Doc page`
   cell (via its title and its `Element type`/`Extension base`
   metadata, parsed with `markdown.rs`) or into the "Doc pages with no
   matching schema type" list (18 pages of a later schema revision:
   modern comments, persons, `Data_Type`, `Sheet_Type`). The
   elements table covers the element-occurrence pages' subject
   matter.
2. **Part list corrections.** The corpus and [MS-VSDX] 2.3.1/2.3.3
   show paths/content types the sketch only approximated: themes live
   at `/visio/theme/theme{N}.xml` (desktop Visio) and `/visio/theme.xml`
   ([MS-VSDX]); content types come from [MS-VSDX] 2.3.3 and observed
   `[Content_Types].xml` files. Added rows for
   `/visio/data/recordsets.xml`, `/visio/data/connections.xml`,
   `/visio/comments.xml`, `/visio/extensions.xml`,
   `/visio/moderncomments.xml`, `/visio/persons.xml`,
   `/visio/solutions/*`, `/docProps/thumbnail.emf`, and the rels
   parts. `/visio/validation_issues.xml` is kept as listed but is not
   observed in the corpus or the spec (content type shown as `—`).
   The catch-all row is counted in the 31 rows.
3. **Attributes table** carries an extra `Declared in` column
   (disambiguates identical rows, e.g. `IX` on `Row` declared in both
   `IndexedRow_Type` and `NamedIndexedRow_Type`); the sort key adds
   the declaring type as a tiebreak after `(parent element, attribute
   name)`.
4. **"Extraction timestamp" is fixed** (2026-10-12, the source
   retrieval date) rather than a wall clock reading, because the task
   also requires byte-identical re-runs. Noted in the header.
5. **`Copyright` in the output.** The schema itself names a cell type
   `Copyright_Type`, and the types table lists it — that is schema
   data, not Microsoft text (AGENTS.md section 4: names and structure
   are derived facts). The unit test asserts the literal absence of
   `Copyright` for fixture output (as the task asks); the runtime
   check additionally allows a forbidden word only when it sits inside
   one of the schema's own identifiers. The only occurrence in the
   generated file is the `Copyright_Type` row.
6. **Wrapper elements stay `preserved-only`** under the literal rule:
   `Shapes`, `Connects`, `PageContents`, `MasterContents`, `Rel`,
   `PageSheet`, `Trigger`, `Text`, `Data1..3` etc. are not in the
   promotion list. Phase 2 probably needs some of these promoted
   (especially `Shapes`/`Connects`/`PageContents`/`MasterContents`);
   the master may promote them in a follow-up before Phase 2 starts.
