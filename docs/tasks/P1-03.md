## Goal

Read the two Fluent UI control-identifier spreadsheets and produce:

- `ui-spec/visio-2016.yaml`
- `ui-spec/visio-365.yaml`
- `ui-spec/diff-2016-vs-365.md` (a structural diff of the two,
  keyed by Fluent control id)
- `docs/parity/controls.md` (every Fluent control id in both
  layouts, with a status of `implemented` / `stub` / `out-of-scope`)

The schema is `ui-spec/schema.json` (ADR 0007, committed in P1-02;
the schema enforces B1: layout ids are Fluent control names, not
command ids). The extractor contract is ADR 0009. The dispatcher
(`xtask/src/extract/mod.rs`, `xtask/src/main.rs`) is already wired
and will print `OK` / `SKIPPED` / `FAIL` per module. Your job is to
fill the four stubs, wire the `jsonschema` validator, and add the
`serde-saphyr` dependency (ADR 0007 M5; do not use `serde_yaml` or
`serde_yml`).

## Outputs

### `ui-spec/visio-2016.yaml` and `ui-spec/visio-365.yaml`

- Top-level shape is `Layout` (ADR 0007). Same schema; different
  `source`, `source_revision`, and contents. **No `extracted:`
  timestamp** (m4: would change on every extract run).
- The `tabs` list contains every Fluent tab that is not a backstage
  tab. Each tab's `id` is the Fluent control name verbatim
  (e.g. `TabHome`, not `home`). Each group has a Fluent `id` too
  (e.g. `GroupClipboard`).
- The `backstage` section contains the File tab's children (rows
  whose `Tab` is `FileNew` or whose Fluent name starts with `File`
  and whose `Control Type` is `tab`). Each backstage tab's `id` is
  the Fluent control name.
- The `context_menus` list contains one entry per Fluent
  `contextMenu` control. Menu `id` = the Fluent `Group/Context Menu
  Name`; controls are the rows whose `Parent Control` points to
  that name. Control `id` = the Fluent control name.
- The `quick_access_toolbar` section contains the rows whose
  `Tab Set` is `Quick Access Toolbar`. Order is by `Policy ID` and
  then by `Control Name` (stable).
- Every control, group, tab, backstage tab, and context menu entry
  has all five reserved fields (`bounds`, `icon_ref`, `keytip`,
  `size_variant`, `visual_notes`) set to `null` (M4: required with
  `type: [<shape>, "null"]` so the screenshot pass fills them in
  without schema changes).
- The `command` field on each control is `null` in this task (P1-04
  fills it in from `commands.yaml`).
- The `aliases` field on each control is a list of alternate
  Fluent ids for the same control across ribbon placements (B1).
  P1-03 picks the primary parent by `tab` match; the other paths
  become aliases. The empty case is `aliases: []`.
- The five "None (...)" placeholder values in the Fluent
  `Control Type` column are mapped to `none` and the row is dropped.
- Labels are copied verbatim (clean-room rule 4: labels are short and
  permitted; descriptions are not committed).

### `ui-spec/diff-2016-vs-365.md`

A markdown table of every Fluent control id (one per row) with columns:

| id | type | in 2016 | in 365 | path in 2016 | path in 365 |

A "path" is `tab / group / control` for ribbons, `backstage / tab /
control` for backstage controls, `menu / control` for context menu
controls, and `qat / control` for QAT controls. Rows are sorted by
`(in 2016, in 365, id)` so identical sets are obvious. The table is
keyed by Fluent id (B1).

A second small table at the bottom lists:

- Total control count in 2016, in 365, in both.
- Number of ids only in 2016, only in 365.

### `docs/parity/controls.md`

A markdown table of every Fluent control id (one per row) with columns:

| id | type | label | path | status |

`status` is one of:

- `implemented`: a `crates/commands` handler exists for this id.
  P1-03 reports `stub` for every row (no commands crate yet); the
  file is regenerated by `cargo xtask extract` in every phase and the
  status is updated when the registry grows.
- `stub`: a Fluent id exists in the layout, but no Ferrogram command
  has been registered for it yet. The UI shows the control disabled
  with a "not yet implemented" tooltip (Phase 4).
- `out-of-scope`: the Fluent id is in one of the layouts but
  Ferrogram will not implement it in the alpha (e.g. coauthoring,
  macros, data linking). These rows are marked by a sibling
  `ui-spec/out-of-scope.txt` (one id per line); the file is
  committed and edited by the master agent. P1-03 may create the
  file with an initial list of obvious exclusions (e.g. `*Coauthor*`,
  `*Macro*`); the master agent is the only one that can change it
  after P1-03 merges.

Sorted by `(status, id)`. Status order: `implemented`, `stub`,
`out-of-scope`. The table is keyed by Fluent id (B1).

## Implementation notes

- **xlsx parsing.** Use `calamine` (MIT) — it is a single-dependency,
  pure-Rust xlsx reader. Add it to `xtask/Cargo.toml`. The
  `read_worksheet` API returns a `Vec<Vec<Cell>>` indexed by
  `(row, col)`; the first row is the header.
- **YAML writing.** Use **`serde-saphyr`** (MIT, pure Rust, no
  `unsafe-libyaml` C dep) — not `serde_yaml` (archived upstream) or
  `serde_yml` (RUSTSEC-2025-0068, RUSTSEC-2026-0333). See ADR 0007.
  All output maps are `BTreeMap` so keys are sorted. The `[key, value,
  child key, child value, ...]` order in the file is therefore
  alphabetical. This matters for the "deterministic output" rule in
  ADR 0009.
- **JSON Schema validation.** Use `jsonschema` 0.x (MIT), the latest
  version as of Phase 1 start. Load `ui-spec/schema.json` once in
  `Schema::load_default`; cache the validator. Each
  `Schema::validate_file` parses the YAML and validates the chosen
  `$defs/{layout,commands,shortcuts}`. The dispatcher validates the
  files written by the fluent, diff and parity extractors.
- **Determinism.** Two runs on the same input must produce
  byte-identical output. The dispatcher has a unit test that
  re-runs the fluent extractor on a fixture and `assert_eq`s the
  two outputs. Failing this test is a blocker. There is no
  `extracted:` field; the source commit is the only timestamp
  (m4).
- **Clean-room.** Copy labels, ids, types, and structural data only.
  Never copy a description (the Fluent xlsx has none; the
  `Tab`/`Group` columns are short labels and are fine).
- **One cell at a time.** The xlsx file's header row index is `1` and
  data starts at row `2`. `Policy ID` is column `I` (1-indexed). Use
  `calamine`'s `Cell::get` to avoid panics on missing values (the
  early rows have empty `Tab` / `Group` / `Parent` columns because
  QAT controls are root-level).
- **Microsoft 365 channel choice.** The task description (P1-01 notes)
  asks us to decide which 365 channel is canonical. Use
  `Current Channel` (1,161 rows) and record the choice in the
  layout's `source_revision`, in a comment at the top of
  `xtask/src/extract/fluent.rs`, and in ADR 0007 (already
  recorded).
