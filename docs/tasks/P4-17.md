   failure branch of the parity generator listed in the report,

**What changed** (test-only; no production behavior change except the
two refactors below, which are behavior-preserving):

1. **Gate runner (goal 1, P4-12 major 5).** `xtask/src/gate.rs` gained
   two seams and lost none of its output: `plan(step) -> Plan` maps
   every step name to pure data (a `Codegen`/`Parity`/`Coverage`/
   `Layers`/`Fuzz` marker or a `Cargo` step with args, one optional
   env var and an optional installed-subcommand requirement), and
   `drive(skip, runner, out)` drives `STEPS` through an injected step
   runner and an injected `Write` sink. `run` is now the two lines
   `parse_args` + `drive(&skip, &mut run_step, &mut stdout())`; the
   fuzz step has the same shape (`fuzz_with(root, probe, build)` with
   the real `fuzz()` as its thin caller). The format strings of the
   step line, the summary rows and the verdicts are copied verbatim,
   so the real gate output is unchanged (pinned by the tests). 17 new
   tests: step selection (all steps run in order, every step's plan is
   pinned, unknown names fail only their step), the `--quick` and
   `--skip` skip rules at run time (skipped steps never reach the
   runner and are reported as `SKIP --skip/--quick`, `codegen` still
   runs), failure aggregation (every step runs after a failure, each
   failure counts once, only the first reason line is shown, `gate:
   RED (n step(s) failed)`), the summary line format (status column,
   `{:<9}` name field, `{:>7.1}s` duration shape), the `run` entry
   point with all steps skipped, the two fast `cargo xtask` steps
   through the real wiring (read-only check modes), and the fuzz
   step's skip/needs-cargo-fuzz/ordered-build/stops-on-failure arms
   over a scratch tree.
2. **Parity error arms (goal 2, P4-12 major 6 + minor 9).** 11 new
   tests in `xtask/src/extract/parity.rs`, one per listed failure
   branch: `run`'s directory-create and atomic-write failures (a
   `docs` file; a `controls.md` directory the temp-file rename cannot
   replace), `generate`'s missing/unparsable input arms, the
   non-list `commands.yaml`, entries without an `id` and without a

   `glob_match` with an uncompileable pattern and `md_escape`'s

3. **Fuzz housekeeping (goal 3, P4-10).** `crates/ui-spec/fuzz/.gitignore`

**Deviations:**

1. `builds_parity_from_real_layouts` no longer deletes and rewrites the
   committed `docs/parity/controls.md`; it runs the same two-run
   determinism assertions over a scratch copy of the committed
   `ui-spec/` inputs. The old body rewrote a committed file from
   inside `cargo test` and raced with the new `the_fast_xtask_steps_pass`
   parity check. All its assertions are unchanged and stronger where
   extended (the written path is now also asserted).
2. `drive` writes the summary through `std::io::Write` instead of
   `println!` (identical bytes). A broken stdout is now an error
   return instead of a panic (AGENTS section 6, "never crash").
3. The `crates/ui/fuzz` seeds live in per-target subdirectories
   (`corpus/settings_json/`, `corpus/shortcuts_map/`) — cargo-fuzz's
   default corpus dirs — because the crate has two targets; the flat
   layout of the single-target `render`/`vsdx` fuzz crates cannot
   separate two targets' inputs.

**Open issues:**

1. **`cargo deny check` fails on `main` (2026-10-17), so the gate's
   `deny` step cannot be green yet.** Three freshly flagged
   *unmaintained* advisories — RUSTSEC-2026-0370 (`zvariant`),
   RUSTSEC-2026-0371 (`zbus_names`), RUSTSEC-2026-0372
   (`zvariant_derive`; all merged into `zbus` 6) — fire on the locked
   `zbus` 5 line under `eframe` -> `egui-winit` -> `accesskit_winit`
   -> `accesskit_unix`. `bans`, `licenses` and `sources` are ok;
   rustsec says "No safe upgrade is available". The fix is in
   `deny.toml` (ignore entries or the unmaintained policy) or a
   dependency-side upgrade; `deny.toml` is not this task's file
   (AGENTS section 6), so it is left to the master. P4-17 changed no
   dependency and no lockfile.
2. `crates/render/fuzz/corpus/` and `crates/vsdx/fuzz/corpus/` are
   flat, but cargo-fuzz auto-loads only `corpus/<target>/`; their seeds
   are used when passed explicitly (`cargo fuzz run <target>
   fuzz/corpus`). Moving them to per-target directories would make the
   layout uniform with `crates/ui/fuzz` (not this task's files).
