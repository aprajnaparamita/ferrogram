## Note from the master

Two corpus findings the ADRs do not cover yet. Handle both in this task and
record the rule as an amendment to ADR 0021 (you own the model side; add the
amendment section to the ADR in your branch).

1. **`Themed` cached values.** Many colour and transparency cells cache the
   literal string `Themed` (for example `<Cell N='FillForegnd' V='Themed'
   F='Inh'/>`, `GradientStopColor` with `F='THEMEVAL()'`). Under ADR 0021
   as written, these would count as kind mismatches, so themed shapes would
   render in the hard default colour. Instead, `CellReader::color` (and the
   number accessor for the `*Trans` cells) must treat `Themed` as "resolve
   from the theme": use the shape's `QuickStyle*` cells (`QuickStyleLineColor`,
   `QuickStyleFillColor`, `QuickStyleShadowColor`, `QuickStyleFontColor`,
   and the matrix cells where needed) against `Document::themes[0]`. Take
   the meaning of the `QuickStyle*` values from the ShapeSheet reference on
   Microsoft Learn (an allowed source) and record it in `docs/sources.md`.
   If a value cannot be resolved, fall back to the hard default with a new
   `WarningKind` (for example `UnresolvedTheme`), not a kind-mismatch warning.
   The theme's format scheme (`a:fmtScheme`) is in scope only as far as the
   colour lookup needs it; line-weight and effect matrices may wait, with an
   open issue.
2. **Colour indices.** Cached colour values are often palette indices, not
   RGB (`<Cell N='LineColor' V='0' F='GUARD(0)'/>`). Documents store
   `ColorEntry` rows only from `IX='24'` up (checked on all 15 corpus files),
   so indices 0..23 must come from `palette`. Look for a Microsoft Learn
   page that lists the default colour indices first (allowed source). If
   none exists, transcribe them from black-box observation and say so.
