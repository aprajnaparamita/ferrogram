## Goal

Define every Phase 1 output format and the code interfaces, so P1-03..P1-07 can run in parallel on disjoint files.

Read KICKOFF.md "Phase 1" for the required outputs:

- `ui-spec/panel-2016.yaml`, `ui-spec/panel-365.yaml`: tabs → groups → controls, plus backstage and context menus. Per control: `id`, `type`, `label`, `parent`, `order`, and reserved empty optional fields `bounds`, `icon_ref`, `keytip`, `size_variant`, `visual_notes` for the later screenshot pass. The format must let that pass enrich data **without schema changes**.
- `ui-spec/schema.json`: JSON Schema validating both layout files.
- `ui-spec/commands.yaml`: our command ids → VisUICmds names and control ids, each with `mapping_confidence: exact | inferred | unknown`.
- `ui-spec/shortcuts.yaml`.
- `ui-spec/diff-2016-vs-365.md`: generated structural diff.
- ShapeSheet table (sections, rows, cells, types, default units) as codegen input for `crates/model`. Choose its path and format.
- `docs/vsdx-inventory.md`: every MS-VSDX part, element and attribute with MVP status supported / preserved-only / later.
- `docs/parity/controls.md`: generated matrix of every control id in both layouts with status implemented / stub / out-of-scope.
- One command, `cargo xtask extract`, regenerates all of it from `reference/`.

## Decisions to make (one ADR each where significant)

1. **Command id scheme** (e.g. `home.align.left`, `shape.rectangle`, `file.save`) and how ids relate to Fluent control ids and VisUICmds names. Every user action is a command in one registry (AGENTS.md section 6).
2. **ui-spec YAML format and JSON Schema**, including how 2016 and 365 layouts share or differ in control ids, and how backstage/context menus are represented. Note which YAML crate the loader uses (licence must pass `deny.toml`) and how the schema is validated in tests (e.g. `jsonschema` crate).
3. **ShapeSheet table format and location**, and how `crates/model` will consume it in Phase 2 (build.rs codegen vs checked-in generated Rust).
4. **Extraction architecture**: module per source under `xtask/src/extract/`, input paths under `reference/`, deterministic output (sorted, stable), how labels are kept short (labels only, never descriptions — clean-room rule 4), what happens when `reference/` is missing (clear error, not panic).
5. **libvisio oracle harness**: build approach (CMake/autotools prerequisites, where the build lives on /Volumes/Dara), how tests invoke it, and that it is optional for the gate (skipped when not built).

### What changed

- **Five ADRs (0006..0010) in `docs/adr/`.** Each captures one of the
  five decisions the task calls out. The decisions are:
  1. **0006 — command id scheme.** Ferrogram's own id space
     (`scope.verb.qualifier`, lowercase ASCII). Distinct from Fluent
     control names and VisUICmds constants. Mapping table is
     `ui-spec/commands.yaml` with `mapping_confidence: exact | inferred
     | unknown`. Reserved scope list (file, edit, view, insert,
     format, home, design, page, review, developer, data, process,
     shape, stencils, help, app) is closed; adding one is an ADR.
  2. **0007 — ui-spec YAML format and JSON Schema.** One schema
     (`ui-spec/schema.json`, Draft 7) validates all four files.
     Five fields (`bounds`, `icon_ref`, `keytip`, `size_variant`,
     `visual_notes`) are required-but-nullable so the later screenshot
     pass enriches data without schema changes. No `description`
     field anywhere (clean-room rule 4).
  3. **0008 — ShapeSheet table.** `ui-spec/shapesheet.toml` is the
     canonical source; a `build.rs` in `crates/model` reads it at
     build time and writes `crates/model/src/shapesheet_table.rs`
     (gitignored, generated). The static `SECTIONS` and `CELLS`
     slices are re-exported from `model` and consumed by `shapesheet`
     and `ui-spec`.
  4. **0009 — extraction architecture.** `xtask/src/extract/` has one
     module per source; all return `ExtractResult<()>`; a
     top-level dispatcher runs them in order, prints
     `OK` / `SKIPPED` / `FAIL` per module. Stubs return
     `Unimplemented { task: "P1-NN" }`. `cargo xtask extract` exists
     and works; a missing `reference/` returns a clean error.
  5. **0010 — libvisio oracle harness.** `tools/libvisio-oracle/`
     with a `build.sh` (POSIX sh), a git submodule pinned to the
     `NOTICE` commit, and a tiny `xtask/src/oracle.rs` wrapper.
     Optional for the gate; `FERROGRAM_REQUIRE_ORACLE=1` enables
     tests that need the binaries.

- **`ui-spec/schema.json` (316 lines, Draft 7).** Defines the
  `controlType` vocabulary (19 entries), the `commandId` pattern
  (dotted lowercase), the `Control` shape (with the five reserved
  fields), the `Layout` / `Commands` / `Shortcuts` top-level

### Open issues for the master agent / follow-ups

- **Microsoft 365 channel choice.** P1-03 will use
  `Microsoft 365/Current Channel` (1,161 rows) as canonical and
  record the choice in `ui-spec/panel-365.yaml`'s `source_revision`.
  The other 365 channels are present in `reference/` but unused.
  If a future phase wants to switch to Semi-Annual Channel, only
  the fluent extractor input path changes; the schema is the same.

- **ShapeSheet build script dependency.** P1-04 will add a
  `crates/model/build.rs` that reads `ui-spec/shapesheet.toml` at
  build time. The build script is on disk only when the TOML
  exists; an empty `SECTIONS = &[]` is the fallback. Master agent:
  when the TOML is first committed, run `cargo build -p
  ferrogram-model` once to populate the generated file (and ensure
  the file is in `.gitignore`).

- **CamelCase split for VisUICmds ids.** P1-04's
  `commands::OVERRIDES` table will need a hand-curated list of
  ~30..50 entries where the algorithm
  `strip(visCmd) + lowercase(first) + dot-split(CamelCase)` gives
  the wrong scope (e.g. `visCmdABarAutoHeight` → `a.bar.auto.height`
  is wrong; it should be `app.bar.auto.height` or similar). P1-04
  will record the override list in its Result section.

- **Schema cross-references.** The JSON Schema does not enforce
  that `commands.yaml`'s `fluent_ids` appear in a layout file (the
  schema validates per-file). The cross-check lives in the P1-06
  loader (`LoadError::CrossReference { kind, id, referenced_by }`)
  and in P1-04's `commands::run`. The master agent's review of
  P1-04 should specifically check that the cross-check runs before
  `commands.yaml` is written.

- **Subprocess for `cargo xtask extract`.** P1-03 will probably
  decide between running the extractors in-process vs as a
  subprocess (subprocess would re-build xtask for every test run).
  P1-02's design is in-process; a follow-up ADR can move to
  subprocess if the in-process time becomes a problem.

- **Coverage ratchet.** xtask coverage is now 59.6%; the ratchet
  in `coverage.toml` is 55.6%. P1-12 will also add tests to xtask
  (its task file lists coverage in its acceptance criteria). The
  master agent should run `cargo xtask coverage --update-ratchet`
  at the end of Phase 1, after P1-12 merges.
