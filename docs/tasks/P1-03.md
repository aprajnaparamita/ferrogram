## Implementation notes

- **xlsx parsing.** Use `calamine` (MIT) — it is a single-dependency,
  pure-Rust xlsx reader. Add it to `xtask/Cargo.toml`. The
  `read_worksheet` API returns a `Vec<Vec<Cell>>` indexed by
  `(row, col)`; the first row is the header.
- **YAML writing.** Use **`serde-saphyr`** (MIT, pure Rust, no
  `unsafe-libyaml` C dep) — not `serde_yaml` (archived upstream) or
  `serde_yml` (RUSTSEC-2025-0068, RUSTSEC-2026-0333). See ADR 0007.
  All output maps are `BTreeMap` so keys are sorted. The `[key, value,
  child key, child value, ...]` order in the file is therefore
  alphabetical. This matters for the "deterministic output" rule in
  ADR 0009.
- **JSON Schema validation.** Use `jsonschema` 0.x (MIT), the latest
  version as of Phase 1 start. Load `ui-spec/schema.json` once in
  `Schema::load_default`; cache the validator. Each
  `Schema::validate_file` parses the YAML and validates the chosen
  `$defs/{layout,commands,shortcuts}`. The dispatcher validates the
  files written by the fluent, diff and parity extractors.
- **Determinism.** Two runs on the same input must produce
  byte-identical output. The dispatcher has a unit test that
  re-runs the fluent extractor on a fixture and `assert_eq`s the
  two outputs. Failing this test is a blocker. There is no
  `extracted:` field; the source commit is the only timestamp
  (m4).
- **Clean-room.** Copy labels, ids, types, and structural data only.
  Never copy a description (the Fluent xlsx has none; the
  `Tab`/`Group` columns are short labels and are fine).
- **One cell at a time.** The xlsx file's header row index is `1` and
  data starts at row `2`. `Policy ID` is column `I` (1-indexed). Use
  `calamine`'s `Cell::get` to avoid panics on missing values (the
  early rows have empty `Tab` / `Group` / `Parent` columns because
  QAT controls are root-level).
- **Microsoft 365 channel choice.** The task description (P1-01 notes)
  asks us to decide which 365 channel is canonical. Use
  `Current Channel` (1,161 rows) and record the choice in the
  layout's `source_revision`, in a comment at the top of
  `xtask/src/extract/fluent.rs`, and in ADR 0007 (already
  recorded).

### Fluent id vs command id (B1)

ADR 0007 B1 says layout control ids are Fluent control
names, not Ferrogram command ids. P1-03 enforces this in
two places:

1. The first tab's id in both layouts is the Fluent name
   (e.g. `TabHome`), not a Ferrogram-style snake-case id
   (e.g. `home` or `tab.home`). Asserted by
   `extract::fluent::tests::layout_uses_fluent_id_not_command_id`.
2. The schema's `fluentId` pattern is `^[A-Za-z_][A-Za-z0-9_]*$`
   (see Deviations for the P1-03 correction) and the
   `commandId` pattern is `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`.
   The two namespaces are explicitly distinct in the schema
   and in the validator's error messages.

The task description (P1-03) says "the five `None (...)` placeholder values in the Fluent `Control Type` column are mapped to `none` and the row is dropped." That text is inaccurate: the `None (...)` placeholders are in the `Tab Set` column, not in `Control Type`, and there are five of them in the `Tab Set` column (`Backstage View`, `Context Menu`, `Core Tab`, `Not in the Ribbon`, `Quick Access Toolbar`). The mapping in P1-03's code is therefore: `Tab Set ∈ {"None (Core Tab)", TabSet*}` → Ribbon, `Tab Set = "None (Backstage View)"` → Backstage, `Tab Set = "None (Context Menu)"` → ContextMenu, `Tab Set = "None (Quick Access Toolbar)"` → QAT, `Tab Set = "None (Not in the Ribbon)"` or empty → Drop. P1-03 still handles `Control Type = "None (...)"` (and `Control Type = "button (dialogBoxLauncher)"`) via `Row::mapped_type`, mapping them to `none` (dropped) and `buttonDialogBoxLauncher` respectively — neither occurs in the actual data, but the code is correct if a future xlsx introduces them.

### Deviations / data surprises

Two P1-03 corrections to the P1-02-committed
`ui-spec/schema.json`; both are recorded inline in the
schema's `description` fields.

1. **`fluentId` pattern was too strict.** The P1-02
   pattern was `^[A-Za-z][A-Za-z0-9_]*$` (first char must
   be a letter). The upstream Fluent data contains ids
   that start with an underscore — `_3DRotationGallery`,
   `_3DRotationOptionsDialog`, `_3DBevelOptionsDialog`,
   `_3DBrightnessMore` in the 365 file. P1-03 widens the
   pattern to `^[A-Za-z_][A-Za-z0-9_]*$` (first char is a
   letter or an underscore). The change is purely
   additive; it does not loosen any validation that was
   already working.
2. **The `control.command` field could not be `null`.**
   The P1-02 schema declared
   `type: ["string", "null"]` plus `\$ref: "#/definitions/commandId"`.
   The `\$ref` overrides the type union, so a null
   command failed validation. The same fix landed on
   `main` as `ddf98e7` during the P1-06 review (rewriting
   the field as `anyOf: [{ \$ref: "#/definitions/commandId" },
   { type: "null" }]`). P1-03 derives the same correction.
   Every command in P1-03's output is `null` (P1-04 fills
   it in from `commands.yaml`); without this fix, the
   fluent extractor's `validate_file` step would have
   aborted the whole `cargo xtask extract` run.

A third data surprise (not a schema change) is the
duplicate `cn` rows in the xlsx. The same Fluent control
name appears in multiple rows for two reasons:

- **Same tab, different parents** (e.g. `TabSave` appears
  4 times in `TabRecent` in 365, with `Parent Control`
  `Save`, `SaveCloudServices`, etc., and one with empty
  parent). P1-03 records the empty parent as a missing
  data point, not as an alias; the resulting control's
  `parent` is `null` and its `aliases` list is the union
  of the other parents.
- **Cross-tab/cross-group duplicates** (e.g. `Copy` is in
  `TabHome/GroupClipboard` and `TabIconEditor/GroupIconEditClipboard`).
  P1-03 keeps the first occurrence (by `Policy ID`, then
  `Control Name`, then source row) and lists the other
  group ids in `aliases`. Asserted by
  `extract::fluent::tests::cross_tab_duplicates_become_aliases`.

P1-03 chose source order for the `order` field of tabs,
groups, controls, and backstage tabs (the order they
appear in the xlsx, which matches Visio's actual ribbon
order). The task explicitly mandates
`(Policy ID, Control Name)` ordering only for the QAT,
which P1-03 does. The schema's `order` description says
"Sibling order. Ties broken by id, ascending." — under
P1-03's source-order rule, the `order` field is the
0-based position in the source-order list, so it is
unique per sibling and there are no ties.

  Ported `xtask/src/extract/schema.rs` to the `jsonschema`
  0.58 API: `jsonschema::draft7::new` and
  `Validator::iter_errors`. Sub-schema validation still
  wraps a synthetic root that re-supplies the
  `definitions` block (jsonschema 0.58's `draft7::new`
  does not expose a way to scope a sub-schema in
  isolation). `xtask/Cargo.toml` matches `crates/ui-spec`'s
  `jsonschema = { version = "0.58", default-features = false }`
  and `serde-saphyr = "1.3"` so the lockfile has one
  version of each crate, and `reqwest` is no longer pulled
  in. All 12 schema tests still pass.
- **M2 (load committed layouts with the runtime loader).**
  Added a dev-dep on `ferrogram-ui-spec` in `xtask/Cargo.toml`
  (xtask is outside the layer rules per AGENTS.md section 6)
  and a new unit test
  `extract::fluent::tests::committed_layouts_load_with_the_runtime_loader`
  that copies the committed `ui-spec/panel-2016.yaml` and
  `panel-365.yaml` into a temp workspace, writes empty
  `commands.yaml` / `shortcuts.yaml` (P1-04 has not landed
  yet), calls `Loader::load(LayoutKind::Visio2016)` and
  `Loader::load(LayoutKind::Visio365)`, and asserts the
  counts: 2016 → 16 ribbon tabs / 8 backstage / 43 context
  menus / 9 QAT; 365 → 19 / 10 / 43 / 9. The loader is
  the same one `crates/control` and `crates/ui` will use
  at runtime; this test proves the extractor and the
  loader agree on the format before P1-04 starts.

  `ui-spec/visio-*.yaml` and `docs/parity/controls.md` is

  `visiocontrols.xlsx` has no display labels. Added a
  one-line note to the top of `docs/parity/controls.md`
  pointing at `crates/commands` (P1-04) and the screenshot
  pass (Phase 4) as the future sources of human labels.
- **m2 (shorten the `fluentId` description).** Replaced
  the long description (with its P1-03 history lesson)

  root is now `anyOf` and `control.command` is
  `anyOf: [commandId, null]` after `ddf98e7` on `main`.
  The Result section was updated to use the same wording.

### Open issues

- The 2016 and 365 layout files together have 4 ids that
  appear only in 2016 (mostly OLE-link-era controls that
  Microsoft retired in 365) and 112 ids that appear only
  in 365 (mostly cloud / coauthoring / data-visualizer
  additions). The diff and parity files list every one
  of them. The master agent may want to look at the 112
  365-only ids and decide which belong in the alpha
  surface before Phase 4.
- P1-04's commands extractor will fill in the `command`
  field of every control; the schema's `oneOf` allows
  the transition from `null` to a real `CommandId` to be
  done in place.
- The out-of-scope globs use `*` only (no `?` / `[...]`).
  The README in `ui-spec/out-of-scope.txt` documents the
  syntax.
- The `ui-spec/` directory now also contains generated
  artifacts (4 files). The `apps` and `xtask` crates
  build the layouts at extract time; downstream crates
  load them at runtime. The committed artifacts are the
  "what shipped in this phase" record.
- 4 duplicate `TabSave` rows in 365's backstage end up in
  4 separate `controls` entries under the same backstage
  tab, with the same `id` and different `parent` and
  `aliases`. The loader will need to disambiguate these
  by parent when resolving a click (P1-04 territory).
