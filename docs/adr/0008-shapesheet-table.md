# 0008: ShapeSheet table format and location

- Status: accepted
- Date: 2026-10-12
- Task: P1-02

## Context

`crates/model` and `crates/shapesheet` need a catalogue of every ShapeSheet
section, row and cell that appears in Visio: its name, the `VisSectionIndices`
it lives at, the row index inside the section, the cell name and the cell's
type and default unit. The catalogue is consumed:

- by `crates/model` when reading and writing `.vsdx` (cell names → XML
  element names),
- by `crates/shapesheet` when the formula engine references a cell by name
  (`Sheet.N!Cell`).

P1-01 found the catalogue already in `reference/`:

- 1082 markdown files under
  `reference/ms-vsdx/office-developer-client-docs/docs/visio/`,
- ~60 `<section>-section.md` files,
- ~700 `<cellname>-cell-<section>-section.md` files,
- section/row/cell indices from `visio.vissectionindices.md`,
  `visio.visrowindices.md` and `visio.viscellindices.md`.

KICKOFF.md says: "A ShapeSheet table of sections, rows and cells with types
and default units, used as codegen input for `crates/model`."

The P1-02 review (M1) found two issues with an earlier draft of this
ADR:

- It used a `build.rs` in `crates/model` that wrote to
  `crates/model/src/shapesheet_table.rs` and silently emitted an empty
  static when the TOML was missing. Cargo build scripts must write
  only to `OUT_DIR`; writing into `src/` is reserved for source
  generation that happens before `cargo build` (e.g. via
  `xtask codegen`). A silent empty fallback also hides real
  failures.
- It listed `crates/ui-spec` as a consumer of the table. `ui-spec` is
  L0 and `model` is L1 (ADR 0002); L0 cannot depend on L1, so
  `ui-spec` cannot use the table at all. (The P1-02 reviewer's
  concern was scope creep: `ui-spec` had no real use for the table;
  it is a command bar-data loader, not a ShapeSheet data loader.)

## Decision

The catalogue is a single **TOML** file committed at
`ui-spec/shapesheet.toml`. It is the source of truth and is **generated** by
the P1-04 extractor from the markdown files under `reference/`. Phase 2 adds
a separate code-generation step (`cargo xtask codegen`) that turns the TOML
into a committed, generated Rust file inside `crates/model/`.

### Phase 1 (this task's scope)

P1-04 produces the committed `ui-spec/shapesheet.toml` and nothing else.
There is no `build.rs` in `crates/model` in Phase 1. `crates/model` and
`crates/shapesheet` in Phase 1 do not consume the table; they have hand-
written section/row/cell enums (the few dozen they need for Phase 2 read
support) and will be extended in Phase 2 with the generated types.

### Phase 2 (follow-up, not P1-02 or P1-04 ownership)

Phase 2 adds `cargo xtask codegen`, a separate dispatcher that:

- reads `ui-spec/shapesheet.toml`,
- writes `crates/model/src/generated/shapesheet.rs` (a
  `pub mod generated { pub static SECTIONS: &[Section] = ..; pub
  static CELLS: &[Cell] = ..; }` or similar),
- has a `--check` mode that fails when the on-disk generated file is
  out of date with the TOML,
- is invoked by `cargo xtask gate` (added in Phase 2) so CI catches
  drift.

The generated file is committed and has the standard
"GENERATED — do not edit. Regenerate with `cargo xtask codegen`."
header. The TOML is the single source of truth; the generated file
is a deterministic transformation of it.

### File path and why TOML

- Path: `ui-spec/shapesheet.toml` (committed, generated by P1-04).
- Format: TOML, parsed by `toml` (MIT/Apache-2.0, already used by xtask
  and in `deny.toml`).
- Reason for TOML: simple key/value, no nesting ambiguity, easy to
  read in diffs, and Rust has a fast zero-dep parser. YAML is overkill
  for a table-of-tables with no lists of mixed records.

### Shape

```toml
# ui-spec/shapesheet.toml
schema_version = 1
product = "visio"
source = "Microsoft Learn ShapeSheet reference (office-developer-client-docs f8c5dfed...)"
source_revision = "2024-04-12 (commit f8c5dfed613fafd2fb8c8f9b1e43454f29517831)"

# One [[sections]] entry per ShapeSheet section.
[[sections]]
name = "Shape Transform"
section_index = 1                     # visSectionObject
kind = "object"                       # "object" | "collection" — distinguishes
                                      # per-shape fixed sections (one row each)
                                      # from repeated-row sections.
description_source = "shape-transform-section.md"  # file under reference/, not committed
default_unit = "Inches"               # default unit for cells in this section

# Cells live at fixed positions in fixed sections (kind = "object").
# For "collection" sections, the same cell set repeats per row.
[[sections.cells]]
name = "PinX"
cell_index = 0                        # local index within the row
type = "Number"                       # "Number" | "String" | "Bool" | "Color" | "List"
default_unit = "Inches"
default_value = "0 in"                # optional
description_source = "pinx-cell-shape-transform-section.md"

[[sections.cells]]
name = "PinY"
cell_index = 1
type = "Number"
default_unit = "Inches"
default_value = "0 in"
description_source = "piny-cell-shape-transform-section.md"

# Example: a collection section (rows repeat).
[[sections]]
name = "Geometry"
section_index = 10                    # visSectionFirstComponent
kind = "collection"
# rows are defined globally so the same row definitions can be referenced
# by every collection section that has them.
rows = ["visRowComponent", "visRowVertex", "visRowLine", "visRowArc", "visRowEllipse", "visRowNURBS", "visRowSpline", "visRowMoveTo", "visRowPolylineTo"]

# Sections may also reference rows that are "owned" by another section
# (e.g. visRowXFormOut is owned by Shape Transform, but its index is
# defined in visio.visrowindices.md globally). The global row table
# captures the index.
[[rows]]
name = "visRowXFormOut"
row_index = 6
section = "Shape Transform"

[[rows]]
name = "visRowLine"
row_index = 2
section = "Geometry"
```

### Consumers in Phase 2+

- `crates/model` consumes the table to translate cell names to XML
  element names when reading and writing `.vsdx`.
- `crates/shapesheet` consumes the table to resolve `Sheet.N!Cell`
  references in formulas.

The P1-02 review confirmed that `crates/ui-spec` does **not** consume
the table. `ui-spec` is a command bar-data loader; the ShapeSheet table is
about document content, which lives entirely below L2.

### Extractor rules (P1-04)

The P1-04 extractor walks `reference/ms-vsdx/office-developer-client-docs/docs/visio/`:

- A file ending in `-section.md` whose name has no `cell-` substring
  is a section. Parse the first paragraph after the `# Title` heading
  for a one-line summary. Cells inside are linked by name.
- A file matching `<name>-cell-<section>.md` is a cell. Parse the
  table that has "Section index" and "Row index" rows for those
  fields. The `description_source` is the file's relative path under
  `reference/`.
- A file matching `<name>-function[-visioshapesheet].md` is a
  function; the functions table is **not** part of `shapesheet.toml`
  in Phase 1 (functions live in `crates/shapesheet` and are extracted
  separately; the function catalogue is a separate codegen output in
  a later phase).
- The three enumeration files (`visio.vissectionindices.md`,
  `visio.visrowindices.md`, `visio.viscellindices.md`) provide the
  integer index for every name.

The extractor outputs sorted sections, sorted cells within a section,
and sorted rows. The output is deterministic: re-running on the same
input produces byte-identical TOML.

## Consequences

- One file, one place to read the ShapeSheet metadata. Easy to diff.
- The TOML is small (estimated ~80 sections, ~700 cells → ~50 KB)
  and parses in <1 ms; codegen cost in Phase 2 is negligible.
- The same `cargo xtask codegen` pattern works for any future
  catalogue (e.g. a function table).
- If Microsoft renames a cell, only the TOML changes; the codegen
  re-emits the new constant. Tests against a corpus catch rename
  errors.
- The TOML is a **derived** file. It is committed (so `cargo
  check` works in CI without `reference/`), but the extractor is
  the only writer.
- The `description_source` field stores the relative path under
  `reference/`, not the content. No Microsoft text is committed.
- No `build.rs` in `crates/model` in Phase 1. Phase 2 introduces
  `cargo xtask codegen` with a `--check` mode and the gate runs it
  on every CI build. The codegen output is committed, so the
  repository has no `src/` files generated by `build.rs`.

## Alternatives considered

- **Hand-write `shapesheet_table.rs` as checked-in Rust.** Rejected:
  700 cells to maintain; humans will make typos; the source of truth
  should be the upstream markdown.
- **`crates/model/build.rs` writing to `src/`.** Rejected by the
  P1-02 review (M1): Cargo build scripts must write only to
  `OUT_DIR`, and a silent empty fallback hides real failures.
- **Put the table in `crates/shapesheet/build.rs` and have model
  depend on shapesheet.** Rejected: violates layering; shapesheet is
  L2 and cannot export to L1.
- **YAML instead of TOML.** Both work; TOML is faster to parse, has
  a stable 1.0 spec, and matches the rest of the workspace (`xtask`
  already uses `toml` for `coverage.toml`).
- **Use a database (SQLite).** Rejected: massive overkill, makes
  read-time joins slower, and the data has no relations beyond
  section → cells.
- **Have the loader parse the TOML at runtime.** Rejected: every
  consumer would need the TOML file at runtime, bloating the binary
  and requiring a lookup path. Build-time codegen is the standard
  pattern and keeps the runtime free of strings.
- **Skip Phase 2's `cargo xtask codegen` and have each consumer
  `include_str!` the TOML.** Rejected: parsing TOML at runtime
  bloats the binary and forces a global lock on the parser; the
  codegen step is a small, well-isolated piece of xtask logic.
