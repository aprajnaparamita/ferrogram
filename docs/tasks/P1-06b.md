## Background

issues". The master decided them as follows:

- **Issues 1 and 2 (schema)**: fixed on `main` in `ddf98e7`. A
  control's `command` may now be `null`, and the schema root is

- **Issue 4 (cross-reference strictness)**: ADR 0007 is right. Every

  layouts and will list 365-only and 2016-only controls.
- **Issue 5 (`ContextMenu.label` doc comment)**: the schema wins. Fix
  the doc comment.

## Goal

1. Change the `fluent_id` cross-reference so it checks against the
   union of the Fluent ids in **both** layouts.
   - `Loader::load(kind)` keeps its signature and return type. It
     reads and schema-validates both layout files, but returns only
     the requested `LayoutSet`. The `control_command` and
     `command_id` checks are unchanged.
   - Add `Loader::load_all(&self) -> Result<LayoutSets, LoadError>`,
     where `LayoutSets { visio_2016: LayoutSet, visio_365: LayoutSet }`
     reads every file once. Add `LayoutSets::get(kind) -> &LayoutSet`.
     Keep `LayoutSet::select` as it is.
   - `CrossReference { kind: "fluent_id", referenced_by, .. }`: make
     the message say "not in any layout".
2. Regression tests:
   - A command whose Fluent id exists only in the 365 layout loads
     without error for both `LayoutKind`s (extend the `good/` fixture,
     e.g. a 365-only control mapped in `commands.yaml`).
   - A Fluent id in neither layout still fails with `kind: "fluent_id"`.
     The `xref-fluent/` fixture needs a `panel-365.yaml` now; add one.
   - A control with `command: null` loads, and appears in
     `CommandLookup::labels` but not in `commands`.
   - An empty `shortcuts.yaml` (`[]`) loads. An empty
     `commands.yaml` loads when no control has a non-null command.
   - Unit tests for `load_all` and `LayoutSets::get`.
3. Fix the `ContextMenu.label` doc comment in `lib.rs` to match the
   schema (1 to 80 characters, never empty).

### What changed

- `crates/ui-spec/src/loader.rs` — the `fluent_id` cross-reference
  now runs against the **union** of the Fluent ids of both layout
  files (ADR 0007 cross-reference 1: "must appear in at least one
  layout"). Every load reads all four documents through the new
  private `read_documents()` (panel-2016, panel-365, commands,
  shortcuts — read and schema-validated exactly once per load), so
  `commands.yaml` may legitimately name a 365-only or a 2016-only
  control. `check_references()` takes the layouts being returned plus
  the precomputed union: `Loader::load(kind)` passes only the
  requested layout (the `control_command` and `command_id` checks are
  unchanged, as the task specifies), `Loader::load_all()` passes both.
  New public API: `Loader::load_all(&self) -> Result<LayoutSets,
  LoadError>`, documented with a doctest.
- `crates/ui-spec/src/lib.rs` — new `LayoutSets { visio_2016,
  visio_365 }` (next to `LayoutSet`, derives `Debug, Clone, PartialEq,
  Default`) with `LayoutSets::get(kind) -> &LayoutSet`; `LayoutSet::select`
  unchanged. `ContextMenu.label`'s doc comment now matches the
  schema: one to 80 characters, never empty (issue 5).
- `crates/ui-spec/src/error.rs` — `LoadError::CrossReference`'s
  `Display` goes through the new `cross_reference_message()`: for
  `kind: "fluent_id"` the message ends in "is not in any layout"
  (the other two kinds keep "is not known"); the `kind` field docs
  describe the union check. Two unit tests pin both wordings.
- `crates/ui-spec/tests/fixtures/` — regression fixtures:
  - `good/ui-spec/commands.yaml`: `edit.redo` now maps the 365-only
    `RedoButton` (the union reading must load for both `LayoutKind`s;
    under the old per-layout check `load(Visio2016)` failed).
  - `good/ui-spec/visio-{2016,365}.yaml`: new `FontSizeLabel`
    control with `command: null` in the Font group of both layouts.
  - `xref-fluent/`, `xref-control/`, `xref-shortcut/`: each gains the
    `panel-365.yaml` the loader now reads. `xref-fluent`'s 365 layout
    also lacks `GhostControl`, so the id is in no layout under both
    readings (the task called for exactly this file).
- `crates/ui-spec/tests/loader.rs` — 16 integration tests (was 11).
  New: `a_command_mapped_to_a_365_only_control_loads_for_both_kinds`,
  `a_control_without_a_command_loads_and_is_labelled_only`,
  `load_all_matches_loading_each_kind`,
  `empty_shortcut_table_loads`,
  `empty_command_table_loads_when_no_control_dispatches_a_command`.
  `unknown_fluent_id_in_commands_is_rejected` now loops over both
  `LayoutKind`s and asserts the "is not in any layout" message.
- Unit tests: `load_all_returns_both_layouts_and_get_picks_one`,
  `load_all_reports_the_same_fluent_id_failure_as_load`,
  `check_references_accepts_an_id_only_the_other_layout_has` (loader),
  `layout_sets_get_borrows_the_kind_matching_set` (lib), plus the two
  `error.rs` message tests. Totals: 55 lib + 16 integration + 2
  doctests = 73 (P1-06 had 61).

### Interpretations (no interface deviation)

- `LayoutSets` lives in `lib.rs` beside `LayoutSet` (it is a public
  data type, not loader machinery); `Loader::load_all` re-exports it
  implicitly through the crate root's existing structure — no new
  re-export was needed because it is defined at the root.
- `load(kind)` keeps its exact signature/return type and now requires
  **both** layout files to exist (it reads both); with neither present
  the `Io` error still names `panel-2016.yaml`, because documents are
  read in fixed file order: 2016, 365, commands, shortcuts.
- `load(kind)` checks `control_command` for the requested layout only
  ("the `control_command` and `command_id` checks are unchanged");
  `load_all` checks both layouts, since it returns both. Both
  behaviours are documented on the methods.
- Fixture control counts moved from 7/8 to **8/9** (the new
  `FontSizeLabel` in both layouts); `controls_per_layout_are_stable`
  pins the new numbers. The P1-06 Result's counts are fixture-derived
  and explicitly allowed to move with the fixtures.
